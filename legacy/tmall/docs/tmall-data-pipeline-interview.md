# 天猫数据接入：面试讲解稿

本文按面试问答组织，覆盖这次改造涉及的每一个技术决策：
为什么这么选、代价是什么、如果不这么选会出什么问题。

---

## 一、整体架构：两条数据通路

这次接入的核心，是把**两种性质完全不同的数据**分别放进适合它们的地方：

```
原始数据
├── 结构化数据（用户、行为日志、复购样本）
│   └─▶ PostgreSQL
│        ├── Silver 层：明细，与 CSV 一一对应
│        └── Gold 层：汇总，供智能问数查询
│
└── 业务知识（口径、限制、抽样说明）
    └─▶ Markdown ─▶ 切片 ─▶ Embedding ─▶ pgvector
                                             │
                                             ▼
                                        混合检索（向量 + 关键词）
                                             │
                                             ▼
                                    RRF 融合 ─▶ 精排 ─▶ Top 5
```

一次问数的完整链路：

```
问题
 ├─▶ 领域路由（零售 / 天猫）
 ├─▶ 意图识别（trend / ranking / breakdown / repurchase / funnel）
 ├─▶ 资产检索（按领域过滤后的指标与数据集）
 ├─▶ 生成 SQL ─▶ AST 安全校验 ─▶ 只读事务执行
 ├─▶ 知识库检索（口径与限制）
 └─▶ 结论 + 图表
```

## 二、为什么结构化数据进 PostgreSQL，业务知识进 pgvector

这是整份设计里最值得说的一处取舍。

### 两者的查询方式根本不同

**结构化数据要的是「算」，不是「找」。**

「按天统计点击量」「哪些商家的购买用户最多」——这些问题的答案
**不在数据里，而是要从数据里算出来**。数据库擅长的是这件事：
`GROUP BY`、`COUNT(DISTINCT ...)`、`ORDER BY ... LIMIT`，
在 100 万行上几秒钟出结果，而且结果是**精确**的。

把这类数据塞进向量库会立刻出问题：向量检索是**近邻查找**，
它返回的是「最像的几条」，不是「精确的聚合值」。
问「总共有多少条行为记录」，向量库给不出答案——它压根没有聚合能力。
就算硬用一个文档存住数字，数据一更新就对不上了。

**业务知识要的是「找」，不是「算」。**

「为什么 11 月的量特别高」「buy 到底算不算订单」「这个漏斗是不是转化漏斗」——
这些答案**已经写在文档里了**，需要的是「从几十段文字里找出最相关的那几段」。
这正是向量检索的强项：用户可能说「加购」「放购物车」「加进购物车」，
字面完全不同但语义一样，关键词匹配会漏，向量检索不会。

### 一个判据

> **答案需要从原始数据算出来 → 数据库。
> 答案已经写在某段文字里 → 向量库。**

选错的后果是不对称的：

- 该进数据库的进了向量库 → 数字开始不精确，而且**没有报错**；
- 该进向量库的进了数据库 → 找不到，但至少是诚实的失败。

### 关键点：两者不能互相替代

这是面试里最容易被追问的地方。

**知识库不能产生数字。** 知识文档里会出现「11 月的量约为常规月份的两倍」
这样的描述，但那是文档作者的描述，不是这次查询算出来的事实。
如果把文档里的数字直接当答案，用户看到的会是一个**过期**的数——
数据重新导入之后文档不会自动更新。

所以系统里有一条硬边界：**数字只来自 SQL 查询结果，
知识库只负责解释这些数字**。而且这条边界不是靠约定，是靠代码结构保证的——
知识检索的产物只流向「解释」节点，`generate_sql` 节点压根收不到它。

**数据库不能解释口径。** 数据库知道「buy 有 60036 条」，
但它不知道「这 60036 条不是 60036 笔订单」。这个区别只有文档写了。

## 三、用户级稳定抽样

### 做法

四个 CSV 文件用**同一条规则**抽样：

```
user_id % sample_modulus == sample_residue
```

默认 `modulus = 55`、`residue = 0`，把 5492 万行日志缩到 998,542 行，
42.4 万用户缩到 7,712 个。

### 为什么不用行号或随机数

**按行号抽**：四个文件的行号含义完全不同。
同一次导入里「第 1、56、111 行」在用户表、日志表、训练集里指向完全不同的东西。
抽出来的用户集合对不上，训练样本里的用户在行为日志里查不到——
数据看起来导进去了，但任何需要关联的分析都是空的。

**按随机数抽**：每次抽到的人不一样，导入结果不可复现，
也没法判断「这份文件是不是已经导过了」。

**按 `user_id` 取模**同时解决三个问题：

| 性质 | 说明 |
| --- | --- |
| 确定性 | 同一份文件、同一组参数，永远抽出同一批人 |
| 跨文件一致 | 训练样本里的用户一定能在用户表和行为日志里找到 |
| 用户粒度完整 | 不会把同一个用户的事件切一半进来 |

### 代价必须说清楚

取模在语义上是**任意**的——取模为 0 的用户并不比别的用户特殊。
这不是业务抽样（不是「抽活跃用户」，也不是分层抽样），
只是把数据缩到本地跑得动的规模。

所以：

- **绝对数量**只代表抽样后的子集。「7,712 个用户」不是平台用户数；
- **比例类指标**受抽样影响小得多，因为抽样是随机的、不针对行为，
  所以比例基本可以代表整体。

**量级要谨慎，比例可以放心一些**——这个区别在给结论时必须讲清楚。

### 抽样是可控的，但漏抽会被发现

校验脚本会数出每张表里「不满足取模条件」的行数。
任何一个文件忘了抽样、或者用了别的列抽样，这个数立刻变成非零。

## 四、COPY 批量入库

### 做法

用 PostgreSQL 的**二进制 COPY**（`asyncpg.copy_records_to_table`），
不做逐行 INSERT。

### 为什么

| 方式 | 101 万行耗时 |
| --- | --- |
| 逐行 INSERT | 分钟级，且把 WAL 写爆 |
| 二进制 COPY | 约 10 秒 |

差距不只是常数因子：逐行 INSERT 每行都要一次往返、一次解析、一次 WAL 记录；
COPY 是一条语句把整批数据流进去，PostgreSQL 走的是专用的批量装载路径。

### 三个实现细节

**1. 全程不解压。** `zipfile.ZipFile.open(member)` 返回边解压边读的流，
1.9GB 的日志不会在磁盘上落副本。省掉的不只是 2GB 空间，
还有「解压到一半失败留下半个文件」这种状态。

**2. 记录是流式的，不是先攒后写。** 生成器逐条产出元组，asyncpg 边消费边写。
内存占用与数据量无关——如果先 materialize 成 list，
101 万个元组的 Python 对象大约要几百 MB。

**3. COPY 落在同一个事务里。** 从 SQLAlchemy 的异步连接里取出底层 asyncpg 连接
（`get_raw_connection().driver_connection`），取出来的是**同一条物理连接**，
所以 COPY 天然加入 SQLAlchemy 已经开启的事务——
这正是「Silver 写入 + Gold 重算 + 成功状态」能同生共死的基础。

### 表头校验为什么必须提前

四个文件的表头**全部校验完**才开始写库。

否则会出现：第一个文件已经 COPY 完了，才发现第四个文件的表头不对。
事务虽然能回滚，但几分钟已经白花；更糟的是报错信息会让操作者
以为「导入到一半坏了」，从而去查一个不存在的问题。

所以文件打开与表头校验是**立即发生**的，只有数据行的产出是惰性的。

### 列顺序也是契约

表头校验比的是**列名加顺序**，不只是列名集合。

因为 `item_id` 和 `cat_id` 都是整数：如果列顺序错了，
按位置取值会把 `item_id` 读成 `cat_id`，类型校验**根本发现不了**，
错误会一路静默传播到 Gold 表。

## 五、事务、幂等、索引与 Gold 层

### 事务：为什么是三个而不是一个

```
事务 A（独立提交）  插入一行 status='running' 的台账
事务 B（主事务）    清空旧 Silver + 写 Silver + 重算 Gold + 改成 'succeeded'
事务 C（仅失败时）  改成 'failed' + 错误分类
```

看上去「一个事务全包」更简单，但它有一个致命缺陷：

> 主事务回滚时，那条记录「这次尝试失败过」的台账行**也会一起回滚**。

结果是失败的导入在数据库里不留任何痕迹，排查时只能翻终端输出。
拆成三个之后：

- **成功状态与数据在同一个事务里提交**，不会出现「数据进去了但状态还是
  running」或反过来的半截状态；
- 失败时 B 整体回滚，Silver 和 Gold 干干净净，不会留下导入一半的数据；
- 台账因此是一份**完整的尝试历史**，包括失败的那些。

### `--replace` 的原子性：两个必须一起修的坑

`--replace` 的语义是「清空旧数据、导入新数据」。它最危险的窗口是
**清空之后、新数据写完之前**——旧数据已经没了，新数据又没进来。

这个窗口上实际踩到了两个独立的坑，而且**第二个比第一个隐蔽得多**：

**坑一：清空与写入被拆成了两个事务。**
清空提交了，后续写入失败回滚，于是 Silver 空、Gold 还是上一批的，
两边对不上而且没有任何报错。旧数据已经不可恢复——它是被一个
**已提交**的事务删掉的。

**坑二：即使合并成一个事务，COPY 仍然可能在自动提交模式下执行。**

这一条是实测发现的：SQLAlchemy 的 asyncpg 方言**不下发显式 `BEGIN`**，
它依赖 asyncpg 的隐式事务，而隐式事务是由「第一条经过方言的语句」
顺带开起来的。如果事务里的第一个动作是绕过 SQLAlchemy、直接调
asyncpg 的 `copy_records_to_table`，就会出现：

```
conn.in_transaction()       → True    （SQLAlchemy 以为在事务里）
asyncpg.is_in_transaction() → False   （数据库其实没在事务里）
```

这次 COPY 就跑在**自动提交**模式下：数据立刻落盘，之后无论怎么
rollback 都收不回来。更糟的是 SQLAlchemy 的回滚会「成功」返回。

实测现象：`--replace` 时清空成功、前三张表 COPY 成功、第四张失败，
回滚之后库里躺着前三张表的新数据。

**修法是让「在事务里」这件事变成显式检查，而不是依赖方言的内部行为**：
写事务开头先用一条经过 SQLAlchemy 的语句把隐式事务开起来，
再断言 `asyncpg.is_in_transaction()`。断言不是多余的——
哪天 SQLAlchemy 改了实现，导入会当场失败，而不是悄悄写坏数据。

**这两条是怎么被发现的？** 不是靠读代码，是靠一个数据库集成测试：
预先放好一套旧 Silver 和旧 Gold，用 `--replace` 覆盖并在中途制造失败，
然后断言旧数据一个字节都没变。

这个测试写出来时是**红的**——它一次就暴露了两个坑。
如果只修了坑一（用户报告的那个），测试依然是红的；
这正说明「先写测试」在这里的价值：报告描述的是症状，测试覆盖的是契约。

### 幂等：判据是内容哈希，不是文件名

判定键是 `(ZIP 的 SHA256, sample_modulus, sample_residue)`。
命中一条 `status='succeeded'` 就直接跳过，不读数据、不写数据库。

为什么用文件内容的哈希而不是文件名或修改时间？
换一份同名文件、或者把同一份文件复制到别的路径，都不该被误判成「导过了」。

**跳过需要同时满足两个条件**：台账里有成功记录，**且**目标表里确实有数据。

这半句不能省。有人手工清过表、或者库从备份恢复过，此时台账说「导过了」
而实际一行都没有。只看台账会报「已导入，跳过」，留下一个**空库**——
这是最坏的一种结果，因为它看起来完全成功。

失败过的记录（`status='failed'`）**不构成跳过理由**：
上一次可能只是因为数据库没起来才失败，没理由让那个失败永久生效。

### 索引

| 索引 | 服务于 |
| --- | --- |
| `ix_tmall_user_events_event_date` | 按天聚合（Gold 每日表） |
| `ix_tmall_user_events_action_type` | 按行为筛选与分组 |
| `ix_tmall_user_events_merchant_id` / `category_id` | 商家、类目维度聚合 |
| `ix_tmall_user_events_user_id` | 用户维度聚合 |
| `ix_tmall_user_events_source_row_number`（唯一） | 重复导入的护栏 |
| `ix_tmall_ingestion_runs_identity` | 幂等判定的四列联合索引 |

Gold 层的每一条聚合都按这几列分组，缺一个就是一次全表扫。

`source_row_number` 的**唯一约束**是刻意加的：它让「同一份文件导入两次」
在数据库层就冲突，而不是依赖调用方自觉。

### 为什么 Silver 表之间没有外键

`tmall_user_events` 与 `tmall_users` 之间不建外键，有三个理由：

1. 抽样规则理论上保证不会产生孤儿，但「理论上不会」正是需要校验的地方。
   外键会把一个**可观测的差异**变成一次导入失败——
   排查时我们更想看到「有 3 个孤儿」而不是「COPY 失败」；
2. 事件表 100 万行，外键检查要在每次写入时逐行维护；
3. 所以用**校验查询**代替外键，`verify_tmall_data.py` 会检查孤儿记录。

### Gold 层：为什么要整表重算

每次导入都在同一个事务里先清空 Gold、再全量重算。

**不是因为简单**：

- 增量更新要先解决「哪条明细属于哪次导入」，而抽取范围由抽样参数决定。
  换一组参数重导，增量逻辑就得先撤销上一批的贡献——
  本质上还是全量重算，只是把复杂度藏起来了；
- **一致性只有全量重算能保证**。增量算错一笔，错误会永远留在表里，
  而且没有任何断言能发现它；
- 成本可以忽略：101 万行聚合成六张 Gold 表，几秒钟。

用几秒钟换「Gold 一定等于它此刻应该等于的东西」，很划算。

### Gold 层真正的意义是权限，不是性能

这一点容易被误解，值得单独讲：

> **Gold 层的存在理由是访问控制。**

智能问数**只允许查 Gold**，明细表不在白名单里。

这不是因为 100 万行扫起来慢（并不慢），而是因为：
只要 `tmall_user_events` 可查，任何 LLM 生成的 SQL 就能把
**某一个用户的完整行为轨迹**拉出来。

把明细留在白名单之外之后，「模型能不能拿到用户级明细」这个问题
在**表这一层**就有答案：不能。不依赖提示词，也不依赖模型的自觉。

代价是明细的灵活性没了。这份数据集没有 session，本来也不支持路径分析，
所以不算损失。

### 一个「合法但错误」的数字：正样本占比

`tmall_repurchase_metrics` 的粒度是「数据集切分 × 标签分组」，
train 因此有 `positive` 和 `negative` 两行。

正样本占比是**整个 train 集**的属性，不是某一行的属性。早先的实现
把它算在了 `positive` 那一行，`negative` 行则是 0。看起来没问题——
毕竟「负样本组的正样本占比」确实是 0 嘛。

问题出在下游：

```sql
SELECT positive_rate FROM tmall_repurchase_metrics WHERE dataset_split = 'train'
```

这条 SQL 会**同时返回两个值**：0.5 和 0。而 0 看起来完全像个合法答案。
一个只会写 `WHERE dataset_split='train'` 的下游（包括模型生成的 SQL）
就有一半概率把「训练集正样本占比」回答成 **0%**。

这是个典型的「不会报错的错误」：没有异常、没有越界、
数字本身也在合法区间里，只是答案是错的。

**修法是两层一起做**：

1. **数据层**：把 train 的两行都写成整体正样本率。无论下游怎么写
   `WHERE`，拿到的都是同一个正确数字。
2. **口径层**：catalog 里的公式明确写成
   `dataset_split = 'train' AND label_group = 'positive'`，
   让「该取哪一行」在口径上就没有歧义。

只做第 1 条也能修掉当前的问题，但第 2 条防的是「将来有人改回按组各算」——
那时公式里的限定条件会让问题在评审阶段就被看见。

**这个坑用测试锁住了**：断言 train 两行的 `positive_rate` 集合是
`{0.5}` 而不是 `{0.5, 0}`，并且专门有一条测试叫
「negative 行的正样本占比永远不是 0」。

## 六、知识侧：切片 → Embedding → pgvector → RRF → 精排

这四份天猫知识文档**沿用项目现有的实现**，没有另建一套向量系统。

### 切片

按 Markdown 结构切：H1 是文档标题，H2 是切片边界，H3 归入所属 H2。

每个切片存三段信息：`文档标题 + 小节标题 + 正文`。
小节标题一起进向量不是冗余——「限制」这个小节标题在文档之间有区分度，
能让「天猫有哪些限制」这类问题命中文档里的限制段落。

超过 1200 字符的小节按段落二次切分，避免向量把一段长文字平均成
一个没有重点的方向。

### 幂等：hash 的对象是「要写进去的东西」

入库时对 `content_for_embedding`（也就是「标题 + 小节 + 正文」）取哈希，
**不是对文件文本取哈希**。

因为：在文件里多加一个空行、调一下缩进，文本哈希就变了，但切片内容一模一样。
用文本哈希会把这种改动判成「文档变了」，于是删掉 44 行再原样插回 44 行，
旧向量的 id 和创建时间全被冲掉，而实际什么都没变。

文档没变 → 整篇跳过，**一次 embedding 都不调**；
文档变了 → 只重算变化的那几个切片（按 `content_hash` 反查复用旧向量）。

复用旧向量时**必须比对 embedding 模型**：换了模型之后旧向量和新向量
不在同一个语义空间里，拿旧向量去比是错的。

### 混合检索与 RRF

两路召回：

- **向量路**：pgvector 的余弦距离，负责「意思像不像」；
- **关键词路**：PostgreSQL 的 `pg_trgm` + GIN 索引，负责「字面对没对上」。

为什么不把两边的分数加权相加？因为它们**量纲不同**：

- 向量给的是余弦距离，0~2 的几何量，挤在很窄的区间里；
- 关键词给的是命中层级分，我们自己定的 0~100 序数，几个离散档位。

加起来等于在比较两个不同单位的数，谁的量级大谁说了算——
而这个「谁大」完全取决于我们当初把权重量成多少。
**那不是检索质量，那是巧合。**

RRF 绕开这件事：**只用名次，不用分数**。

```
score(chunk) = Σ 1 / (k + rank_i(chunk))     k 默认 60
```

在第 i 路排第几，就贡献 1/(k+名次)。k 把高名次之间的差距压平
（第 1 名和第 2 名的贡献是 1/61 和 1/62，几乎一样），
让「多路都命中」比「一路排第一」更能拉开差距。

这正是融合想要的：被多路同时命中的切片是「大家都能找到」的东西，应该排前面。

### 精排

召回 Top 20 之后，用小模型做交叉编码精排，选 Top 5。

**召回是双塔，精排是交叉编码。** 双塔里问题和文档各自独立算向量，
问题那边的向量在算的时候完全不知道候选文档长什么样——它快，
但「两段文字像」不等于「这段回答了那个问题」。交叉编码把问题和候选
**拼在一起**送进模型，逐条判断相关性，准得多，代价是每条候选都要单独推理。

所以链路分两步：

```
全库 71 条 ──向量 + 关键词召回（快，能扫全库）──▶ 20 条 ──精排（慢，但准）──▶ 5 条
```

**精排只拿原问题，不拿改写后的问题。** 召回阶段用改写问题是对的
（多几条路，多捞点候选），但最终判断相关性必须回到用户真正问的那句话——
改写是模型换的说法，它可能把限定词抹平，拿它去精排，选出来的候选就偏离了原意。
**召回可以发散，排序必须收敛到原问题。**

**精排失败要退回 RRF 顺序。** 精排是增益步骤、不是必需步骤。
它挂了（超时、限流、5xx）时召回候选仍然有效，只是排序不如精排准。
所以正确的反应是退回 RRF 顺序继续回答，而不是让整个问答失败。

## 七、SQL 与 RAG 怎么协同

这是整个系统设计里最核心的一条边界。

### 分工

| | SQL | RAG |
| --- | --- | --- |
| 提供 | **数字** | **口径、背景、限制** |
| 来源 | Gold 汇总表 | Markdown 知识文档 |
| 回答 | 「多少」 | 「怎么算的」「为什么」「有什么限制」 |

一个真实例子：

> **问**：天猫各行为的量是多少？

- SQL 查出：click 881,857、cart 1,343、favorite 55,306、buy 60,036；
- RAG 提供：`buy` 是行为记录不是订单；漏斗不是 session 顺序漏斗；
  这是抽样后的子集、时间含双十一。

最终回答是**两者结合**：

> 抽样范围内共 998,542 条行为记录，其中点击 881,857 条、购买 60,036 条。
> 注意购买数是行为记录数而不是订单数——数据里没有订单号；
> 且这是用户抽样后的子集，时间窗口含双十一大促，不是自然周期。

只给数字，听到的人一定会按自己熟悉的电商口径去理解，
而那个理解在大部分情况下是错的。

### 三条硬边界

**1. 数字只来自 `query_result`。** 知识文档里的数字是文档作者的描述，
不是这次查询算出来的事实。数据重新导入之后文档不会自动更新。

**2. 知识库不能替代数据库查询。** 「销售额是多少」必须走 SQL；
知识库回答的是「销售额怎么算」。

**3. 表名字段名以 catalog 和 SQL 校验器为准。** 知识文档里出现的
`tmall_funnel_metrics.user_count` 只是解释文字，**绝不进入 SQL 生成**。
这不靠自觉——本模块的产物只流向解释节点，压根没有通往 `generate_sql` 的边。

### 知识库挂了不能拖垮问数

知识检索失败时，数字部分照常返回，只是少了口径解释。
所以 State 里 `knowledge_error` 是一个**独立字段**，不是 `error`——
`error` 仍然只表示「问数流程本身失败了」。

## 八、领域隔离：为什么天猫表和零售表不能 JOIN

项目里现在有两套数据：

| | 零售样例数仓 | 天猫 IJCAI 2015 |
| --- | --- | --- |
| 时间 | 2025 全年 | 2014 年 5~11 月 |
| 主体 | 客户 / 商品 / 区域 / 订单 | 匿名用户 / 商品 ID / 商家 ID |
| 有金额吗 | 有 | **没有** |

### 为什么必须显式禁止

`orders JOIN tmall_user_metrics` 这条 SQL：

- 两张表**都在**白名单里，语法完全合法；
- 不会报任何错；
- 会返回一个数字。

但这个数字把 2014 年的行为记录和 2025 年的订单金额连在了一起，
**没有任何业务含义**。

这类错误的可怕之处正是它不报错。所以必须显式禁止。

### 三层拦截

| 层 | 手段 |
| --- | --- |
| 资产检索 | 按问题路由出的领域过滤，模型根本看不到另一个领域的表名 |
| Agent SQL 校验 | `validate_sql_draft` 检测跨领域引用 |
| 数据服务 | `safe_query.validate_safe_select` 独立检测（第二道防线） |

后两层都从 `app/services/data_domains.py` 取领域划分，规则只写一份——
两份手抄的规则迟早在某次改动后分叉，而分叉的表现是
「校验层放行、执行层拒绝」，用户看到一句莫名其妙的未授权。

### 领域路由为什么用规则，不用模型

和「要不要查知识库」同一个理由，而且这里更硬：

- **可测试**：规则是纯函数，给定问题就能断言领域。让模型判的话，
  同一句话今天 retail 明天 tmall，测试只能写得很宽松；
- **绝不能判错**：领域判断决定了后面允许查哪些表。判错的后果不是
  「答得不好」，而是「拿天猫的行为数去解释零售的销售额」；
- **可解释**：命中哪个词能直接写进事件流；
- **成本**：每个问题少一次模型调用。

代价是规则会漏判。所以**默认值放在零售上**：
漏判的后果是天猫问题走了零售口径，下游会因为查不到匹配资产
给出一句诚实的「没有匹配的数据资产」，而不是编一个答案。
反过来把默认值放在天猫上，就会让所有现有的零售问题突然找不到资产——
那是破坏性的。

### 一个具体的取舍：「复购」算哪个领域

需求把「复购」列为天猫识别词，但零售目录里也登记了复购率指标，
现有的一批零售问题正是靠它命中的。

把「复购」判成天猫，会让那些问题突然查不到资产。

所以「复购」被登记为**共享词**：它本身不决定领域，只在和其他词组合时起作用。
实践上这不影响天猫问题的识别——「天猫的复购」「复购样本的标签分布」
都带着别的天猫词，照样路由到天猫。

**这是个刻意的取舍，不是遗漏**，写在了 `domain.py` 的模块文档里。

## 九、数据集限制：怎么避免得出错误结论

这是整份工作的收尾，也是最容易出事的地方。

### 数据里没有什么

| 缺失 | 因此**不能**算 |
| --- | --- |
| 价格、优惠、运费 | GMV、销售额、客单价、利润 |
| 订单号 | 准确订单量 |
| 数量 | 销量件数 |
| 商品名、商家名、类目名 | 「卖得最好的是什么」这类需要名称的回答 |
| 地区 | 地域分析 |
| 物流、退款 | 履约分析、退款率 |

数据里只有**整数 ID**。ID 可以排序、可以去重计数，但映射不到任何可读名称。

### 三个最容易犯的错

**错误一：把 `buy` 当订单。**

`action_type = 'buy'` 表示「这个用户在这个商品上发生了购买行为」。
同一个人同一天同一件商品可以有多条 buy 记录，数据里也没有订单号把它们归并。

把 `buy_count` 叫成「订单数」之后，所有依赖它的判断
（客单价、每单价件数）全部失去依据。

**错误二：把行为占比当转化率。**

数据里没有 session，算不出「点击之后加购再购买」的路径转化率。

能算的只有用户级去重口径：「点击过的人里有多少也买过」。
把它讲成「转化漏斗」会让听众以为存在一条可优化的路径，
而数据并不支持这个结论。

**错误三：把历史复购当成复购标签。**

「复购」在这份数据里被三个不同的东西共用过，必须分清：

| | 复购 | 购买广度 | train 集的 `label` |
| --- | --- | --- | --- |
| 字段 | `repeat_buy_flag` | `multi_merchant_buy_flag` | `label` |
| 含义 | 在**同一个商家**买过 ≥2 次 | 在 **≥2 个不同商家**买过 | **未来**是否会在该商家复购 |
| 时间口径 | 已经发生的事实 | 已经发生的事实 | 尚未发生的预测目标 |

复购与购买广度**会给出相反的答案**：在 10 家店各买 1 次的人广度拉满、
复购为零；只在一家店买了 5 次的人正好相反。

实现里这两个字段曾经是**同一个** `repeat_buy_flag`，而它算的是广度。
那是个静默的口径错误——数字看起来正常，结论全是反的。
现在两者分开，并且有一组「互为反例」的样例数据钉住它：
一个用户只在一家店买两次，另一个用户在两家店各买一次。

`repeat_buy_flag` 为真也**不等于** `label` 会是 1：
前者是历史行为，后者是待预测的目标。

### 避免错误结论的四种手段

**1. 表结构就挡住。** 明细里出现一个叫 `amount` 的列，等于在邀请下游算出
一个错的数。所以天猫表里**一个金额字段都没有**，有一条测试专门扫描
表名和列名里的 `amount` / `price` / `gmv` / `quantity` 等关键词。

**2. 白名单挡住明细。** 智能问数只能查 Gold，模型拿不到用户级明细。

**3. 知识库写清限制。** 四份文档里反复说明「有什么、没有什么、因此不能算什么」，
并且这些文档在**问数时会被检索出来**——问天猫漏斗时一定会带上
「这不是 session 顺序漏斗」这条限定。

**4. 目录里不登记算不出来的指标。** 指标目录里没有 GMV、没有订单数。
登记一个查不到的口径比不登记更糟：模型会照着它生成一条永远失败的 SQL。

### 一个反向的例子：cart 只有 1,343 条

抽样后加购只有 1,343 条，明显少于收藏（55,306）和购买（60,036），
看起来不符合直觉。

这时正确的做法是**先验证自洽性**，再考虑业务解释：

```
click + cart + favorite + buy
= 881,857 + 1,343 + 55,306 + 60,036
= 998,542
= 日志总行数 ✓
```

总数能对上，说明没有漏行也没有重复计数。抽样是按用户取模的，
不会单独针对某一种行为。所以这是数据集本身的分布特征，不是导入出错。

遇到「看起来不合理」的数字，**先验证它是否自洽，再考虑业务解释**——
而不是先假设数据错了。

## 十、如果被问到「这套东西的边界在哪」

诚实地说清楚三件事：

**1. 抽样是任意划分，不是业务抽样。** 取模为 0 的用户不比别人特殊。
绝对数量只代表子集，比例类指标才比较可信。

**2. 行为漏斗不是 session 漏斗。** 这是数据本身的限制，不是实现的取舍。
要算真正的转化漏斗，需要带 session_id 的埋点数据。

**3. 领域路由是规则，会漏判。** 默认值放在零售是为了不破坏既有功能；
真要做得更准，需要引入分类模型或者让用户在界面上显式选择领域。

把边界讲清楚比把能力讲大更有说服力——因为听的人迟早会发现边界，
提前讲出来，说明这些边界是**想过之后有意接受**的，而不是没看到。
