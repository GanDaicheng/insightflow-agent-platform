# 天猫数据集抽样与数据质量

> 文档类型：数据质量说明
> 适用范围：天猫 IJCAI 2015 数据集的本地产副本
> 使用对象：数据分析、智能问数 Agent、取数开发

## 1. 为什么要抽样

原始日志有 **5492 万行**，压缩包约 360MB，解压后接近 2GB。
本地开发环境里全量导入既不必要也不方便：分析要看的是趋势和分布，
不是每一个用户。

所以本地保存的是**按用户抽样后的子集**。抽样参数在导入时记录在
`tmall_ingestion_runs` 台账里，可以随时追溯。

## 2. 怎么抽的：用户级取模

抽样规则只有一条：

```
user_id % sample_modulus == sample_residue
```

默认参数是 `modulus = 55`、`residue = 0`，即 `user_id % 55 == 0`。

### 为什么按 `user_id` 取模，而不是按行号或随机数

**按行号抽**不行：四个文件的行号含义完全不同。同一次导入里「第 1、56、111 行」
在用户表、日志表、训练集里指向的是完全不同的东西，抽出来的用户集合对不上。
结果就是训练样本里的用户在行为日志里查不到——数据看起来导进去了，
但任何需要关联的分析都是空的。

**按随机数抽**也不行：每次运行抽到的人不一样，导入结果不可复现，
也无法判断「这份文件是不是已经导过了」。

**按 `user_id` 取模**同时解决了这两个问题：

- **确定性**：同一份文件、同一组参数，抽出来的永远是同一批人；
- **可复现**：换一台机器、换一个时间跑，结果完全一致；
- **跨文件一致**：四个文件用同一条规则，「训练样本里的用户」
  一定能在「用户表」和「行为日志」里找到；
- **用户粒度完整**：不会把同一个用户的事件切一半进来。

### 代价要说清楚

取模在语义上是**任意**的：取模为 0 的用户并不比别的用户特殊。
这不是业务抽样（不是「抽活跃用户」也不是「分层抽样」），
只是为了把数据缩到本地能跑得动的规模。

因此这带来一个必须声明的限制：

> **绝对数量只代表抽样后的子集，不能当成平台整体规模。**

说「7712 个用户」时必须明白，这是抽样后的用户数，不是平台用户数。
比例类指标（比如「购买用户占点击用户的 42%」）受抽样影响小得多，
因为抽样是随机的、不针对行为，所以比例基本可以代表整体。
**量级要谨慎，比例可以放心一些**——这个区别在给结论时很重要。

### 四个文件必须用同一条规则

用户表、行为日志、训练集、测试集都用 `user_id % modulus == residue`。
任何一个文件忘了抽样、或者用了别的列抽样，
都会在导入后的校验里被发现：校验脚本会把每张表里
「不满足取模条件的行数」数出来，只要有一行不符合就报错。

## 3. 已知的数据质量处理

导入过程中做了几处归一化。它们都会改变原始值，所以必须写清楚：

| 原始情况 | 处理方式 | 为什么 |
| --- | --- | --- |
| `brand_id` 为空字符串 | 存为 `NULL` | 存 0 会让「无品牌」和「品牌 ID = 0」合并成一组 |
| `cat_id` | 改名为 `category_id` | 全项目统一命名 |
| `seller_id` | 改名为 `merchant_id` | 全项目统一命名 |
| `time_stamp` = `0511` | 存为 `2014-05-11` | 原值只有月日，年份由数据集说明确定 |
| `action_type` = `0/1/2/3` | 存为 `click/cart/favorite/buy` | 编码本身没有可读性 |
| `test` 集的空 `prob` | 存为 `NULL` | 原始数据整列为空，不是缺测 |

### 校验是严格的，不是尽力而为

导入时对以下四项做**严格校验**，任何一处不符都会中止导入，不会静默跳过：

1. **表头**：列名、顺序、列数必须与登记完全一致。
   列顺序错了不会报类型错误（`item_id` 和 `cat_id` 都是整数），
   所以顺序也属于契约的一部分。
2. **字段类型**：`user_id`、`item_id` 等必须是整数，空值只在允许为空的列上接受。
3. **日期**：必须是四位 `MMDD` 且是 2014 年的**真实存在**的日期。
   `0230` 这种「格式对、日期不存在」的值会被拒绝。
4. **`action_type`**：只能是 0~3。未知取值直接报错，
   不会归到 `click`——静默归类会污染整个漏斗的分母。

## 4. 抽样后的规模（默认参数 55 / 0）

| 项 | 原始行数 | 抽样后行数 |
| --- | --- | --- |
| 用户表 | 424,170 | 7,712 |
| 行为日志 | 54,925,330 | 998,542 |
| 训练样本 | 260,864 | 4,700 |
| 测试样本 | 261,477 | 4,858 |

行为分布：

| 行为 | 记录数 |
| --- | --- |
| 点击 `click` | 881,857 |
| 加购 `cart` | 1,343 |
| 收藏 `favorite` | 55,306 |
| 购买 `buy` | 60,036 |

日期范围：**2014-05-11 ~ 2014-11-12**。

这些数字记在代码里的登记表里（`app/services/tmall_analytics.py`）。
换一组抽样参数时，登记表里没有对应基准线，校验脚本会报告
「跳过规模断言」而不是失败——参数是调用方的自由选择，不是错误。

### 关于 `cart` 只有 1343 条

加购的记录数明显少于收藏和购买，看起来不太符合直觉。
这是**这份数据集本身**的分布特征，不是导入出错：

- 四条行为之和正好等于日志总行数（881857 + 1343 + 55306 + 60036 = 998542），
  说明没有漏行也没有重复计数；
- 抽样是按用户取模的，不会单独针对某一种行为。

遇到这类「看起来不合理」的分布，正确的做法是先验证它是否自洽
（总数能不能对上），再考虑业务解释——而不是先假设数据错了。

## 5. 抽样留下的两个坑

### 坑一：不能按天相加用户数

`user_count` 在天级和周期级是两个不同口径：

- `tmall_daily_metrics.user_count`：**当天**去重的用户数；
- `tmall_funnel_metrics.user_count`：**整个周期**去重的用户数。

把每天的用户数相加会得到「人次」，远大于真实的去重用户数。
两个数都对，混用必错。

### 坑二：小样本维度上的比例不稳定

抽样后只剩 7712 个用户。当按某个维度细分时（比如「某个类目 + 某种行为」），
组内可能只有几十条记录，算出来的比例波动很大。

给出这类细分比例时应当说明样本量。样本量很小的比例不适合用来做决策，
它更可能反映的是抽样噪声而不是真实差异。

## 6. 重复运行是安全的

同一份 ZIP（按 SHA256 识别）配同一组抽样参数，成功导入过一次之后，
再次运行会被自动跳过，一行数据都不会改。

判定依据是 `tmall_ingestion_runs` 里的一条 `status = 'succeeded'` 记录，
**同时**要求目标表里确实有数据。两个条件缺一不可：
只看台账的话，有人手工清过表之后会得到「已导入，跳过」——
留下一个空库，而且看起来完全成功。

失败过的记录（`status = 'failed'`）不构成跳过理由：
上一次可能只是因为数据库没起来才失败，没有理由让那个失败永久生效。
